# Neon Bastion – Projektwissen für Claude Code

Neon-Incremental-Tower-Defense im Browser (Desktop, iOS, Android). Live unter https://neonbastion.de, Vorschau unter https://neonbastion.de/beta/, Arbeitsstand unter https://neonbastion.de/bottest/ (GitHub Pages aus `docs/`, Repository `Akaino/NeonBastion`).
Dieses Dokument ist die Übergabe aus der bisherigen Entwicklung in einem claude.ai-Chat. Lies es vollständig, bevor du etwas änderst.

## 1. Zusammenarbeit mit dem Nutzer

- **Sprache:** Deutsch, du-Form. Alle Texte im Spiel auf Deutsch, mit deutschen Anführungszeichen „…“ und typografischem Apostroph ’.
- Der Nutzer testet auf **iPhone und MacBook**. Mobile first, Hochformat, Touch und Maus gleichwertig.
- Er will **Belege statt Behauptungen**: Balancing-Änderungen mit der Simulation (`sim/`) begründen und vorher/nachher zeigen.
- Er gibt Feedback in kurzen Sätzen. Bei Unklarheit lieber einmal kurz nachfragen als in die falsche Richtung bauen.
- **Jede Änderung vor dem Ausliefern testen** (`python3 tests/run_all.py`), Versionsnummer erhöhen, dann deployen.
- Ehrlich bleiben: Wenn etwas nicht geprüft wurde oder nicht geht, sag es.

## 2. Befehle

```
python3 build.py                 # baut die Testausgabe dist/web/ (komplette Website inkl. beta/), veröffentlicht nichts
python3 build.py --bottest       # zusätzlich docs/bottest/ → Arbeitsstand unter neonbastion.de/bottest/, darf unfertig sein
python3 build.py --beta          # zusätzlich docs/beta/  → Vorschau unter neonbastion.de/beta/, das echte Spiel bleibt unverändert
python3 build.py --release       # zusätzlich docs/       → komplette Website (Spiel, Rechtsseiten, beta/)
python3 tests/run_all.py         # alle Browser-Tests (Playwright, Chromium), 4 gleichzeitig, ca. 30 s
python3 tests/run_all.py --jobs 1  # nacheinander (ca. 90 s), um Wackler einzugrenzen
node sim/sim.js --seeds 8        # Karriere-Simulation, Zeiger ruht (Idle-Spieler), Auswertung in sim/ergebnisse/
node sim/sim.js --seeds 8 --zeiger zielt   # Bot zieht den Impuls alle 0,25 s auf die dichteste Gruppe (Idealspieler); --zeiger aus = kein Impuls
node sim/sim.js upgrades --at 25,50,75   # Wirkung einzelner Upgrades an Kontrollpunkten
node sim/sim.js aeste --seeds 3 --stunden 4 --zeiger zielt   # Ast-Vergleich: Karriere mit jeder Kombination der fünf Skilltree-Äste
node sim/sim.js probe --at 25,45,70 --runs 10              # Probe am festen Spielstand: Sekunden statt Minuten; --gegen <src-Ordner> vergleicht zwei Fassungen
node sim/sim.js probe --at 75,95 --anteile --knoten b5c=5  # --anteile: Schadensanteile je Quelle; --knoten: Knotenstufen setzen; --held, --frei: Held bzw. Turm einsetzen
node sim/sim.js welt2 --stunden 4 --seeds 3 --varianten richtung:80,ring:130   # Gitterfestung: Karriere je Aufstellung (Bauweise:Abstand); --tuerme, --aeste, --ausbau; --stand 40 --runs 6 = Probe am festen Stand
```

```
npm run format                   # Prettier über src/, sim/, tools/ (Stil: .prettierrc.json)
npm run lint                     # ESLint über src/js und sim (eslint.config.mjs) – muss ohne Befund bleiben
```

Voraussetzungen: Python 3, Node.js ab 18, `pip install playwright && playwright install chromium`, einmal `npm install` (nur Entwicklungswerkzeuge: Prettier, ESLint, Babel-Parser; das Spiel selbst hat keine Abhängigkeiten).
Testen im Browser: `python3 -m http.server -d dist/web 8000` und http://localhost:8000 öffnen. **Direktes Öffnen der Datei geht nicht mehr** – Module lädt der Browser nur über einen Webserver. Die Tests laufen gegen `dist/web/` und starten sich dafür selbst einen Server (`tests/_web.py`).

## 3. Beta und Release

Der Nutzer testet auf iPhone und MacBook im Browser. **Jede Änderung am Spiel geht zuerst in die Beta und erst auf sein „Release“ auf die Hauptadresse.** Artefakte werden nicht mehr verwendet (er kann sie am Handy nicht öffnen).

**Nichts bleibt nur lokal.** Der Nutzer will jeden Stand im Browser ansehen können (Vorgabe vom 14.11.2026: „Lokal gebaut und nicht in der Beta sollte es zukünftig nicht mehr geben“). Ist eine Änderung noch nicht reif für die Beta – etwa mitten in einem mehrstufigen Balancing mit Messläufen –, geht sie nach `/bottest/`: `python3 build.py --bottest`, Tests, Commit „Bottest vX.Y.Z: …“, Push. Im Bericht immer sagen, was unter `/bottest/` liegt und was daran noch fehlt. Sobald sie reif ist, in die Beta.

Beta (nach „Umsetzen“):
1. `VERSION` in `src/js/core/version.js` erhöhen (Schema 0.MINOR.PATCH; Features → MINOR, reine Fixes → PATCH).
2. `python3 build.py --beta && python3 tests/run_all.py`
3. Commit „Beta vX.Y.Z: …“ (Quelltext, Tests, `docs/beta/`), Push auf `main`. **Kein Tag, `docs/index.html` nicht anfassen.**
4. Prüfen, dass `https://neonbastion.de/beta/` die neue Version ausliefert, dem Nutzer Bescheid geben.

Release (wenn der Nutzer „Release“ oder „deploy“ sagt):
1. `python3 build.py --release && python3 tests/run_all.py`
2. Commit „Release vX.Y.Z“, Tag `vX.Y.Z`, Push auf `main`.
3. Prüfen, dass `https://neonbastion.de` die neue Version ausliefert: `index.html` verweist auf den Ordner `vX.Y.Z/` (Pages cached einige Minuten).

`docs/` und `dist/` sind Build-Ausgaben. Nie direkt bearbeiten, immer `src/` oder `assets/` ändern und neu bauen. `dist/` ist nicht im Repository.

Beta und Bottest sind dasselbe Spiel in einem eigenen Ordner, zusätzlich mit Entwicklermodus (`build.py`). Das Spiel erkennt die Stufe zur Laufzeit am Pfad `/beta/` bzw. `/bottest/` (`STAGE`, `IS_BETA` in `js/core/version.js`): Kennzeichnung „Beta“ bzw. „Bottest“ an der Version, eigener Spielstand `neon-bastion-beta` bzw. `neon-bastion-bottest`, Knopf „Live-Spielstand übernehmen“ in den Einstellungen (kopiert `neon-bastion-v1` in den Beta-Spielstand, nie umgekehrt), `noindex`. Reine Werkzeug-Änderungen (Tests, Simulation, Dokumentation) brauchen keine Beta.

## 4. Architektur

Kein Framework, keine Laufzeit-Abhängigkeiten. Seit 0.31.0 (Umbau vom 15.11.2026 auf Wunsch des Nutzers: „Warum ist das nicht ordentlich?“) besteht das Spiel aus ES-Modulen und wird in getrennten Dateien ausgeliefert. Vorher klebte `build.py` sieben Dateien mit gemeinsamem globalem Namensraum zu einer einzigen HTML-Datei zusammen; ältere Abschnitte dieses Dokuments nennen noch die alten Dateinamen (`core.js`, `game.js`, `ui.js`, `shell.html`).

```
src/
  index.html      Gerüst: nur Markup, bindet css/ und js/main.js ein (Platzhalter %V%, %ROOT%, %HEAD%, %SCRIPTS% füllt build.py)
  css/            base, hub, hud, menus, modal
  js/
    main.js       Einstieg des Spiels (lädt alle Module)
    dev-main.js   Einstieg des Entwicklermodus – nur Beta und Bottest
    logic.js      die Spiellogik ohne Oberfläche, Grafik und Ton – das lädt die Simulation
    core/         version (VERSION, STAGE), util, format (fmtN, fmtD), save (freshSave, loadSave, Store), stats, dev-hooks (Dev)
    data/         Tabellen und Konstanten: currencies, prestige, nodes, balance, heroes, towers, drones, enemies, drops, bosses
    run/          Run (Klasse, Kern) und Methodenpakete: combat, towers, waves, base, heroes, drones, enemies, impulse, drops, zones; util
    world2/       Welt 2: data, nodes, save, stats, Run2
    render/       Renderer (Kern) und Methodenpakete: sprites, towers, base
    audio/        bus, synth, sfx, music-data, music, track, sound (Snd)
    ui/           dom (Schattenbaum, $), state (save, run, W, R, Perf, persist), common, preview, hub, hud, input, build, tree, heroes, fleet, towers, codex, achievements, nova, worlds, settings, main (Start und Hauptschleife)
    dev/          inject, hooks, perf, tools, mode, perf-start
```

Regeln:

- **Schichten** (von unten nach oben): `core`/`data` → `run` → `world2` → `render` → `ui` → `dev`; `audio` kennt nur `core`. **Spiellogik (`core`, `data`, `run`, `world2`) darf weder Oberfläche noch Grafik, Ton oder Entwicklermodus importieren** – die Simulation lädt genau diese vier Ordner in Node. Grafik und Ton greifen nicht auf den Spielstand der Oberfläche zu: die Oberfläche reicht ihnen, was sie brauchen (`R.hubNodes`, `Vol` über `syncSound`).
- **Große Klassen sind aufgeteilt:** `Run` und `Renderer` stehen mit Konstruktor und Kern in ihrer Datei; die übrigen Methoden liegen als Pakete (`export const runWavesMethods = {…}`) in Nachbardateien und werden mit `Object.assign(Run.prototype, …)` angehängt. Eine neue Methode gehört in das passende Paket.
- **Veränderliche Variablen eines Moduls** (`save`, `run`, `paused`, `speed`, `W`, …) ändert ein anderes Modul nur über den Setter (`setRun(x)`, `setPaused(true)`); lesen geht direkt über den Import. Jede `let`-Variable der obersten Ebene hat einen Setter.
- **Entwicklermodus** liegt vollständig in `js/dev/` und wird nur von Beta und Bottest geladen (`dev-main.js`). Das Spiel kennt ihn nur über das leere Objekt `Dev` (`core/dev-hooks.js`: `Dev.stats`, `Dev.wave`, `Dev.openSettings`) und das leere `Perf` in `ui/state.js`. `build.py` bricht ab, wenn Entwickler-Code im echten Spiel landet.
- **Auslieferung:** `build.py` kopiert `src/js` und `src/css` unverändert in einen Ordner mit der Versionsnummer (`v0.31.0/js/…`), damit ein Browser nie Dateien zweier Versionen mischt, und schreibt `index.html` sowie `css/fonts.css` mit den passenden Pfaden. Ein Bündler ist nicht im Einsatz.
- **Tests und Konsole:** Module haben keine globalen Namen. Beta, Bottest und die Testausgabe `dist/web` laden deshalb zusätzlich `js/expose.js` (von `build.py` erzeugt): Es macht alle exportierten Namen als Eigenschaften von `window` sichtbar, veränderliche mit ihrem Setter. So funktionieren `save`, `run`, `paused=true`, `Perf.live()` in Tests und in der Konsole der Beta weiter. Das veröffentlichte Spiel lädt `expose.js` nicht.
- **Stil:** Prettier (120 Zeichen, einfache Anführungszeichen) und ESLint; beide müssen sauber sein. Bezeichner sind noch die kurzen aus der alten Fassung (`S`, `e`, `updEnemies`) – umbenennen ist ein eigener, späterer Schritt.

Wichtige Konzepte:

- **Welt-Kontext `W`** in `ui/state.js` (`WORLDS[1|2]`): liefert Knoten, Währungen, Spielstand-Teil (`W.s()`), Stats, Türme und Run-Klasse der aktiven Welt. Neue Welten hier andocken.
- **Spielstand:** `localStorage['neon-bastion-v1']`. Welt 2 liegt in `save.w2`. `loadSave` füllt fehlende Felder aus `freshSave` auf. **Spielstände dürfen nie kaputtgehen**: neue Felder immer mit Standardwert, Migrationen in `loadSave`.
- **Run-Logik ist DOM-frei** und läuft unverändert in Node (`sim/bot2.js` lädt `src/js/logic.js`). Das muss so bleiben. `run.headless=true` überspringt Effekte (Partikel, Zahlen, Ringe) für die Simulation.
- Feste Logik-Taktrate 1/60 s im Spiel, Geschwindigkeit 1×/2×/4×/8× über mehrere Schritte pro Frame. In der Simulation `dt=0.05`. **Nicht 0.1** – dann treffen Projektile nicht mehr zuverlässig.
- Erweiterungspunkte in `Run`, die `Run2` überschreibt: `reward(e)`, `energyMul(e)`, `towerStats(type,l)`, `towerSlots()`, `hpScale(w)`, `dmgScale(w)`, `milestone(w)`, `updWaves(dt)`, `updTowers(dt)`.
- **Oberfläche im Schattenbaum** (`ui/dom.js`): Alles außer dem Spielfeld liegt in einem Schattenbaum, damit fremde Skripte im Browser keine Änderungen sehen (siehe Abschnitt 8). `$`/`$$` suchen dort und im Dokument.

**So wurde umgebaut (zum Nachvollziehen):** 1. Entwicklermodus aus dem Spielcode in eine eigene Datei, 2. Prettier über alles, 3. ein Einmal-Werkzeug (Babel) hat jeden Baustein der obersten Ebene anhand einer Zuordnungstabelle einem Modul zugewiesen, mit Bereichsanalyse die Importe ermittelt und fremde Zuweisungen in Setter umgeschrieben, 4. Stilregeln und Gerüst getrennt, Bau und Tests angepasst. Das Spiel selbst wurde dabei nicht verändert: Der Fingerabdruck eines Karriere-Laufs der Simulation (2 Seeds bis Welle 45, sortierte Runs-Tabelle) und eine Probe an drei Spielständen sind vor und nach dem Umbau identisch. Das Werkzeug liegt in der Git-Geschichte (`tools/zerlegen.cjs`, Commit `f9bd2ed`).

## 5. Gameplay-Systeme (Stand 0.36.0 in der Beta; live ist 0.30.1)

**Weltenkarte** (seit 0.33.0, Vorgabe des Nutzers vom 15.11.2026, `WORLD_MAP` und `renderWorlds` in `ui/worlds.js`, `worldOpen(id)` in `world2/save.js`): Welten schalten sich nicht mehr über Welle 100 frei, der Knopf „Welten“ ist von Anfang an da. Die Karte sieht aus wie der Skilltree: „Kern“ in der Mitte, fünf Welten im Kreis darum, weiter außen hinter jeder Welt ein verdeckter Platz („?“) für eine **weitere Version dieser Welt**. Antippen zeigt unten eine Karte mit Beschreibung, Rekord, Weltenbonus und „Welt betreten“. Zustände: Neon-Sektor offen; **Gitterfestung im echten Spiel „Demnächst“, in Beta und Bottest spielbar** (`worldOpen(2)` hängt an `STAGE`; ein Spielstand, der in der Gitterfestung stand, startet im echten Spiel im Neon-Sektor, `save.w2` bleibt erhalten); Welt 3 „Arcade“ und Welt 4 „Classic Tower Defense“ „Demnächst“ mit kurzer Beschreibung; die fünfte Welt ist verdeckt (kein Name, kein „Demnächst“). **Offen, mit dem Nutzer zu klären: Inhalt und Bedingung der zweiten Versionen** – die Plätze sind reine Platzhalter. Die Test-Freischaltung der Gitterfestung im Entwicklermodus (`#bW2Test`, `Dev.w2`) gibt es nicht mehr; das Feld `save.w2test` bleibt ohne Wirkung im Spielstand. Soll die Gitterfestung ins echte Spiel, genügt `worldOpen`. Test: `tests/test_weltenkarte.py`.

**Weltenkarte als Startseite (seit 0.34.0, Rückmeldung des Nutzers: die erste Fassung war „lieblos und steril“, Zahlen statt Namen, Größe sprang beim Antippen):** Das Spiel startet auf der Karte (`openWorlds` in `ui/main.js`), „Weiterspielen“ bzw. „Welt betreten“ führt ins Menü der Welt, der Knopf „Welten“ dort zurück. Mit `#hub` in der Adresse geht es direkt ins Menü – `web()` in `tests/_web.py` hängt das für alle gewöhnlichen Tests an, `web(pfad, karte=True)` lässt die Startseite. Jede Welt hat einen eigenen Knoten mit Umriss und bewegtem Motiv (`ART` in `ui/worlds.js`: Sechseck mit Drohnen, Festung mit Gitter und Abtaststrahl, Sternenflug mit Schiff, Feld mit Weg und marschierenden Gegnern, Nebelwirbel), der Name steht im Knoten, „Aktiv“/„Demnächst“ als Schild darunter. Hintergrund: Sterne, Leuchten je Welt, drehende Bahnen, Energiepuls vom Kern zu offenen Welten. Alles reine CSS-Animation im Schattenbaum, `prefers-reduced-motion` schaltet sie ab. **Die Karte wird nur beim Öffnen aufgebaut; Antippen ändert Klassen und die Infokarte** (`renderSheet`), die Infokarte hat eine feste Mindesthöhe (`#wsheet`), `touch-action: manipulation` verhindert den Doppeltipp-Zoom. Nur der Trefferkreis `.hit` eines Knotens nimmt Klicks an – Tests klicken deshalb auf `[data-w="…"] .hit`. Eine neue Welt braucht: Eintrag in `WORLD_MAP` (mit `lines`), Motiv in `ART`, Stilregeln in `css/menus.css`.

**Welt 1 „Neon-Sektor“:** Basis in der Mitte, Gegner (Schwärmer, Brecher, Fernkämpfer, Elite, Boss alle 10 Wellen, **Doppelboss alle 25 Wellen**) aus allen Richtungen. Drohnen spawnen aus der Basis. Vier Helden (Klinge, Schützin, Arkanist, Wächterin) agieren selbstständig, müssen freigeschaltet werden, haben Stufen (bis 60) und Aufstiege (bis 5). Der **Impuls** ersetzt das Tippen (siehe unten), „Autofeuer“ lässt zusätzlich die Basis selbst schießen. Nächste Welle startet nach 9 s auch mit lebenden Gegnern → Runs enden, wenn die Basis den Schaden gestauter Gegner nicht mehr aushält.

- **Sechs Helden** (seit 0.26.0): neu sind **Kopfjäger** (8 Prismen; wählt das zäheste große Ziel – Elite, Hüne, Boss – und trifft es mit dreifachem Schaden, `HUNT_MUL`; Fähigkeit „Fangschuss“: ein Schuss mit zwölffachem Schaden) und **Ingenieurin** (40 Kerne; solange sie lebt, +25 % Energie aus besiegten Gegnern, `engiAt`; Fähigkeit „Verstärker“: 6 s lang nehmen Gegner im Radius eines Turms +30 % Schaden, `ampT`). Ein neuer Held braucht: Eintrag in `HEROES`, Feld in `freshSave().heroes`, Methode `ai_<id>` in `Run`, Form in `Renderer.heroSprite`, Test. Der Bot schaltet die beiden nicht frei; `probe --held kopfjaeger` setzt einen Helden mit Stufe und Aufstieg des letzten Teamplatzes ein. Probe (je 16 Runs, Rekord 46/52/76/97): Kopfjäger −0,2/±0/−0,3/−1,0, Ingenieurin +0,2/+0,5/−0,2/−1,6 Wellen gegenüber dem ersetzten Helden (Arkanist bzw. Wächterin) – gleichauf.
- **Währungen:** Splitter (jeder Gegner), Kerne (Elite, alle 5 Wellen), Prismen (Bosse, Meilenstein alle 10 Wellen, 0,6 % Elite-Drop), Sternenstaub (erster Bosssieg ab Welle 20 je Zyklus, ab Welle 30 jeder Bosssieg), Quanten (Supernova).
- **Stand 0.32.0 (Rückmeldung des Nutzers zur Abschluss-Testliste, 15.11.2026), 82 Knoten:**
  - **Zweite Währung** (`EXTRA`, `EXTRA_DEEP`, `nodeCost2`, `nodeCosts` in `data/nodes.js`; Bezahlen über `payAll` in `ui/common.js`): Der Nutzer bemerkte, dass späte Knoten beim Freischalten nur wenige Kerne oder Prismen kosten und sich sofort hochkaufen lassen (Kernreaktor: 20 Kerne bei 480 Kernen Ertrag je Run). Jetzt kostet jede Stufe ab Tiefe 6 zusätzlich die nächsthäufigere Währung (Kerne-Knoten Splitter, Prismen-Knoten Kerne, Sternenstaub-Knoten Prismen; Mengen je Tiefe aus dem Ertrag je Run abgeleitet), dazu 18 ausdrücklich genannte frühere Knoten (z. B. Zweiter Platz +3 Kerne, Geschütze +300 Splitter, die vier Verbund-Knoten +6 Prismen). Die Zusatzkosten wachsen mit demselben Faktor wie die Hauptkosten. Welt 2 hat keine. Karriere (4 Seeds, ruht) vorher → nachher: einfache Kaufregel Welle 50 nach 2 h 17 → 2 h 54 min, Welle 100 nach 12 h 26 → 15 h 58 min; Kaufregel nach Nutzen Welle 100 nach 9 h 54 → 10 h 5 min. Wer gezielt kauft, wird also kaum gebremst.
  - **Heldensaga** (`h7c`, fünf Stufen, `HERO_SAGA`): erhöht den Exponenten des Kampfrauschs weiter. Helden-Anteil am Schaden bei Rekord 76/97: 15 → 21 % und 13 → 20 %.
  - **Flotte:** Stehen alle Klassen auf 0 %, baut die Basis keine Drohnen (vorher Jäger). Reparaturdrohnen zeigen jede Heilung als grünen Strahl. Messung (`probe --flotte …`, je 16 Runs): mit 20–40 % Reparaturdrohnen spät 10–30 % weniger nachgebaute Drohnen und +1 bis +2 Wellen bei Rekord 76/97, früh im Rauschen.
  - **Abwurf-Boni wirken 10 s statt 5 s** (dem Nutzer waren 5 s nicht spürbar); die Reparatur gibt weiter insgesamt 30 %.
  - **Magnet** (Welle 83): zieht den Impuls-Zeiger mit 70 Einheiten je Sekunde zu sich, solange der Zeiger näher als 280 ist (`MAG_R`, `MAG_PULL`); der Stör-Turm hebt das auf. Damit 29 Gegnerarten, 31 Einträge in der Enzyklopädie.
  - **Enzyklopädie mit Detailansicht** (`CODEX_HOW`, `codexDetail` in `ui/codex.js`): Knopf „Werte und Verhalten“ an jedem besiegten Eintrag zeigt Leben, Schaden, Tempo und Beute auf der Rekordwelle samt Verhältnis zum Schwärmer, dazu Verhalten und Gegenmittel; bei Bossen Aufladezeit und Abklingzeit. Ein neuer Gegner braucht einen Eintrag in `CODEX_HOW`.
  - **Erfolge:** 33 (neu für Mörser, Giftträger, Scharfschütze, Spiegel, Gespann, Magnet).
  - **Supernova mit Schauspiel** (`supernovaShow` in `ui/nova.js`, etwa 2,8 s): Nova, schwarzes Loch zieht alle Elemente des Menüs in die Mitte, dort wird zurückgesetzt, dann spuckt es das Menü mit den Quanten-Upgrades aus. `supernova()` bleibt die Fassung ohne Schauspiel (Tests, `prefers-reduced-motion`).
- **Verbund mit den Helden (0.29.0, 81 Knoten):** Messung der Schadensanteile (`probe --anteile`) zeigte: Ab Welle 70 trug der Impuls 65–86 % des Schadens, Basis-Geschütze und Flotte fast nichts – selbst dreifacher Drohnenschaden brachte bei Rekord 76/97 keine Welle. Ursache: „Heldenimpuls“ gibt dem Impuls den Heldenschaden-Bonus obendrauf, und der wächst spät enorm (Faktor 1.060 bei Rekord 76, 32.900 bei Rekord 97, weil Knoten und Supernova-Boni multiplizieren). Der Nutzer wollte eher die anderen Äste aufwerten als den Impuls schwächen. Deshalb drei weitere Knoten nach demselben Muster, je fünf Stufen (`F5_MAX`), Kosten 1/1/2/2/2 Sternenstaub: „Feuerleitstand“ `b5c` (Geschütze, Autofeuer, Schockwelle), „Heldengeschwader“ `u5c` (Drohnen), „Kampfrausch“ `h5c` (nur die eigenen Treffer der Helden, Exponent `HERO_SELF`). Jede Stufe ist derselbe Faktor: Stufe l gibt (1+Bonus)^(l/5) (`bond` in `stats()`), damit keine Stufe einen Sprung macht; das gilt jetzt auch für `f5` (Stufe 5 unverändert). Mit linearer Aufteilung brachte schon Stufe 1 fünf bis sieben Wellen. Ergebnis an Rekord 97 (ruht): Basis 2 → 18 %, Flotte 11 → 39 %, Helden 14 → 14 %, Impuls 73 → 30 %, erreichte Welle 96,6 → 107,9 (alle 15 Stufen zusammen). Karriere (4 Seeds, ruht) 0.28.1 → 0.29.0: Welle 75 nach 8 h 3 → 7 h 29 min, 100 nach 13 h 21 → 12 h 13 min, **Welle 150 vorher von keinem Seed erreicht, jetzt von allen vier nach 55 h 54 min** – ohne die Knoten flachte das Spiel nach Welle 100 ab. Ast-Vergleich (5 Seeds, 4 h, zielt): allein Basis 31, Flotte 35, Helden 29, Impuls 31; alle fünf 61 statt 67, weil der Bot den seltenen Sternenstaub auf vier Verbund-Knoten verteilt (Bot-Eigenart „kauft das Billigste“). Mit `--kauf nutzen` (gleicher Lauf): alle fünf 75, ohne Basis 77, ohne Flotte 76; als letzter Ast Basis −2, Flotte −1, Helden +9, Impuls +23, Ertrag +28 – die Verdünnung ist also eine Eigenart der einfachen Kaufregel. **Für Aussagen über Kombinationen künftig `--kauf nutzen` mitmessen** (der Nutzer hat zu Recht nachgefragt). Klicks machen keinen Schaden mehr. Start alle 2 s, Knoten „Taktgeber“ (`f1b`, 36 Stufen, −8 % je Stufe) bis 0,1 s. Schaden je Impuls = Grundschaden × 4 × √(Intervall/2): schneller heißt schwächer je Treffer, der Schaden pro Sekunde steigt über alle Stufen etwa auf das 4,5-Fache (Konstanten `IMP_*` in `core.js`). **Sonderfähigkeiten zählen Impulse bzw. Schüsse, nicht Treffer** (Vorgabe des Nutzers: wer nichts trifft, wartet wieder n ab): „Taktschlag“ (`f3a`, früher „Combo“) verstärkt jeden 5. Impuls, „Überladung“ und „Weltenbrecher“ zählen Impuls und Autofeuer gemeinsam. In der Simulation steuert `--zeiger ruht|zielt|aus` den Zeiger (`aimPointer` in `sim/bot2.js`).

**Entwicklermodus nur in Beta und Bottest** (seit 0.25.1, Vorgabe des Nutzers; seit 0.31.0 als eigene Module in `js/dev/`, siehe Abschnitt 4): Code-Abfrage, Testhilfen und Leistungsmessung liegen dort; ihre Bedienelemente setzt `dev/inject.js` beim Laden in die Einstellungen ein. Tests, die den Entwicklermodus oder die Gitterfestung brauchen, laufen deshalb gegen `dist/web/beta/index.html` mit dem Spielstand `neon-bastion-beta`. Die Simulation lädt nur `src/js/logic.js` und damit keinen Entwicklermodus.

## 8. Fallstricke aus der bisherigen Entwicklung

- **Ruckeln in Safari im Sekundentakt – geklärt am 15.11.2026:** Ein fremdes Skript im Safari des Nutzers (im Zeitverlauf des Web-Inspektors als „Timer … Installed — line 18:427051“ zu sehen; unsere Seite hat keine so lange Zeile, das Skript ist nicht von uns; ob Erweiterung oder Safari selbst, ist offen) beobachtet das Dokument und arbeitet nach jeder Änderung höchstens einmal pro Sekunde 50–150 ms lang, sichtbar als langer „Composite“. Beweis: `Perf.aus('frz')` (alle Textänderungen einfrieren) ließ die Ruckler sofort auf 0 fallen; die ganze Seite ausblenden (`leer`) half nicht. Auslöser waren unsere laufenden Textänderungen (Anzeige im Run zehnmal pro Sekunde, Banner je Welle, Messanzeige zweimal pro Sekunde). **Lösung seit 0.30.0/0.30.1:** Die gesamte Oberfläche (alles in `#app` außer dem Spielfeld `#cv`) zieht beim Start in einen Schattenbaum (`UI` in `ui.js`, Träger `#ui`; die Stilregeln werden hineinkopiert, Regeln am `<html>`-Element wie `:root[data-wtheme=…]` auf `:host(…)` umgeschrieben, das Thema wird zusätzlich am Träger gesetzt); Änderungen darin sieht ein Beobachter des Dokuments nicht. 0.30.0 hatte nur Anzeige, Banner, Hinweise und Messanzeige umgezogen – danach ruckelte es nur noch beim Klicken durch die Menüs (Messung des Nutzers), deshalb seit 0.30.1 alles. `$`/`$$` suchen in beiden Bäumen; seitenweite Ereignisbehandlung muss `e.composedPath()[0]` statt `e.target` nehmen. **Regel für künftige Arbeit: Im laufenden Run darf sich am Dokument außerhalb des Schattenbaums nichts ändern** – `tests/test_stille_seite.py` prüft das mit einem MutationObserver. Neue laufend aktualisierte Elemente gehören in `#hud` oder in die Liste in `UI`. Tests greifen mit `$(…)` statt `document.querySelector(…)` zu. Falsche Fährten davor (alle widerlegt): Zwischenspeichern, Ton-Bausteine, Größe des Dokuments, AdBlock als alleinige Ursache, Speicherbereinigung. Lehre: nicht raten, sondern früh den Zeitverlauf des Web-Inspektors und Schalter in der Konsole (`Perf.live()`, `Perf.aus(name)`, `Perf.an()`) nutzen.
- **Zwischenstand davor (AdBlock-Verdacht):** Mit ausgeschalteter Erweiterung 5 statt 90 Ruckler in 90 s. Die Erweiterung sucht jede Seite im Sekundentakt ab (Abstand der Ruckler = 1 s + Dauer der Suche); das läuft im Hauptthread der Seite und dauert länger, je größer das Dokument ist. Gegenmaßnahmen in 0.29.2: Das Skript nimmt sich nach dem Start selbst aus dem Dokument (`document.currentScript.remove()` in `shell.html`, Dokument 40 KB statt 290 KB), und `show()` leert verlassene Menüs (`DYN` in `ui.js`; 330 statt bis zu 2.200 Elemente). **Ob das mit eingeschalteter Erweiterung reicht, muss der Nutzer messen.** Lehre: Bei Rucklern außerhalb des Spielcodes zuerst nach Erweiterungen fragen; das Dokument klein halten (keine Menüs im Hintergrund stehen lassen). Warum es anfangs manchmal nicht ruckelte und nach dem macOS-Update kurz weg war, ist nicht geklärt. Der Ruckeltest (`tools/ruckeltest.html`) zeigte in seiner ersten Fassung nichts (Ton lief nicht, kleines Dokument); die zweite Fassung hat Stufen für Wiedergabe-Sitzung und großes Dokument.
- **Verlauf der Suche (zweiter Anlauf am Nachmittag):** Am Nachmittag kam es zurück: nach längerem Spielen auf 4×/8× Ruckler von 125–145 ms im Sekundentakt, stotternder Ton, auch direkt nach dem Neuladen; nach Beenden von Safari besser, in einem frischen Safari aber nach etwa einer Minute wieder 55–75 ms. Aktivitätsanzeige: Tab 43 % CPU, obwohl das Spiel je Bild höchstens 1 ms rechnet – der Rest fällt im selben Prozess an (dort läuft die Tonerzeugung). Maßnahmen in 0.29.1: `Track` in `audio.js` trennt alle Ton-Bausteine eines Effekts oder einer Note, sobald sie verklungen sind (vorher wurde nie `disconnect()` gerufen; auf „ended“ ist in WebKit kein Verlass, deshalb zeitgesteuert über das späteste `stop(t)`), und `pagehide` schließt den AudioContext. **Die Maßnahmen haben den Grund-Ruckler nicht beseitigt:** Messung des Nutzers auf 0.29.1 zeigt weiter 43–60 ms im Abstand von 1,04 s, schon nach 10 s im Hub und in allen Abschnitten der Ursachensuche. Neuer Verdacht (ungeprüft): die Safari-Erweiterung „AdBlock for Safari“ (in seiner Prozessliste zu sehen) – ein Inhaltsskript, das die Seite im Sekundentakt absucht, liefe im Hauptthread der Seite, außerhalb des Spielcodes, und unsere Seite trägt 260 KB Skript im Dokument. Prüfen: Erweiterung aus, und `ruckeltest.html` (kleines Dokument). Zum Eingrenzen gibt es `tools/ruckeltest.html` (→ `beta/ruckeltest.html`): startet leer und schaltet große Leinwand, Ebenen, Zeitgeber, Speichern, Ton-Unterbau und Töne einzeln dazu. Ergebnis des Nutzers abwarten.
- **Früherer Stand (vormittags, nach macOS-Update vorübergehend weg):** Nach dem Update auf macOS 27.2.1 und Neustart laut Nutzer weg. Ursache nicht geklärt; die Ursachensuche zeigte 7 Ruckler je 8 s in jedem Abschnitt, auch bei „alles aus“, während testufo.com im selben Safari flüssig lief. Falls es wiederkommt: zuerst Neustart, dann Messung mit den Testhilfen. Verlauf: etwa alle 2–3 s, auf dem iPhone nicht. Mit Playwright-WebKit nicht nachstellbar (Median 17 ms, Speichern 0–1 ms, auch mit zweitem Tab). Im selben Takt läuft nur das Zwischenspeichern (`pendT>2` in `loop`, schreibt den ganzen Spielstand nach `localStorage`). Messung des Nutzers (0.21.1, Safari 26.5, Fenster 1716×861, Leinwand 3432×1722): Ruckler von 55–80 ms genau alle 1,06 s, auch im Hub ohne Run, vollständig außerhalb des Spielcodes („Rest“); Logik, Zeichnen, Musik und Speichern je 0–1 ms. Das Speichern ist also nicht die Ursache. Seit 0.21.2 gibt es in den Testhilfen die „Ursachensuche“ (`Perf.scan`): schaltet nacheinander Messanzeige, Zeichnen, Spielfeld, Ton und CSS-Animationen ab und zählt je Abschnitt die Ruckler. Keine Playwright-Fenster mit `headless=False` öffnen – sie erscheinen auf dem Bildschirm des Nutzers.

- **Klicks gehen verloren, wenn ein Knopf per `innerHTML` neu aufgebaut wird**, während er gedrückt ist. HUD-Elemente einmal aufbauen, danach nur `textContent` ändern (siehe `updBuildBtn`, `updPhase`).
- **Keine Zeitlupe** beim Bauen – fühlt sich wie Lag an. Bauen pausiert stattdessen das Spiel.
- `data-world` war am `<html>`-Element gesetzt und hat jeden Klick als „Welt betreten“ gewertet. Theme-Attribut heißt jetzt `data-wtheme`.
- Kryo + Permafrost konnte Gegner dauerhaft einfrieren → 2 s Immunität nach dem Auftauen (`frzImm`).
- Sturmfront-Rückstoß konnte Gegner endlos pendeln lassen → seltener/schwächer, während Sturmangriff aus.
- Der Nutzer hat oft aus Versehen das Turm-Menü geöffnet. Aktionen auf dem Spielfeld deshalb erst beim Loslassen auslösen und nur, wenn der Finger sich nicht bewegt hat.
- Fernkämpfer außer Reichweite + Reparatur → Patt. Helden/Drohnen priorisieren Fernkämpfer (`threat()`), Welt 2 hat die Sturmregel.
- Musik klang „schief“: Delay-Zeit darf nicht mit dem Tempo moduliert werden (Tonhöhen-Leier). Melodie nur aus Akkordtönen auf betonten Zählzeiten, keine absichtlichen Dissonanzen. Der Nutzer reagiert empfindlich auf unsaubere Musik.
- Bitcrusher schneidet leise Signale auf null → Signal vor dem Crusher verstärken (ist umgesetzt).
- Effekte, die der Nutzer „lasch“ fand: zu viel Hall, Filter-Resonanz („ping“). Knackige, verzerrte, wiedererkennbare Sounds bevorzugt.
- Performance: kein `shadowBlur` pro Objekt und Frame, stattdessen gecachte Glow-Sprites. Kein `Math.hypot` in heißen Schleifen (`hyp()` nutzen).
- Schriften lokal (`assets/fonts`), nicht von Google laden (Datenschutz in Deutschland).

## 9. Designvorgaben des Nutzers

- Neon-Stil, „ordentlich“, keine matschigen einfachen Formen. Top-down, Basis in der Mitte.
- Inkrementeller Fortschritt ist das Wichtigste: stetig, keine Sprünge um 15 Wellen durch 1–2 Upgrades, Spiel praktisch endlos.
- Idle muss funktionieren; aktives Zielen mit dem Impuls ist ein Bonus, keine Pflicht. Kein Klicken oder Tippen für Schaden.
- **Jedes Upgrade zeigt eine Vorher-Nachher-Vorschau** (Skilltree, Helden, Türme, Supernova).
- Seltenere Währung für höhere Upgrades; seltenere Währungen nie vor häufigeren.
- Türme: Einzel-Upgrade per Antippen im Run bleibt so, wie es ist.
- Welt 2: keine festen Wege, Richtungsanzeige, Umbauphase, begrenztes Verschieben.
- Musik soll mit der Welle zackiger werden und „fast Stress verursachen“, aber sauber klingen.
